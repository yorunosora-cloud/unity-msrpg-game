# 19. 커뮤니티 문제 제작 + 범용 쿠폰 보상 시스템

---

## 세계관 맥락

- 지금까지 R&E(연구·교육) 문제는 **관리자(제작자 본인)만** 만들었다. 인게임 관리자 패널(90) 또는 에디터 도구로 문제를 저작해 PlayFab TitleData(`problems`)에 발행하면 전 플레이어에게 자동 배포된다.
- 받은 피드백: **플레이어 커뮤니티를 운영해 거기서도 문제를 공급받자.** 문제의 다양성·수급량을 늘리고 커뮤니티 참여 동기를 만드는 것이 목적이다.
- 커뮤니티는 **네이버 카페**(무료·운영 편의)로 게임 바깥에서 굴린다. 제출·별점 투표·채택은 전적으로 카페에서 이뤄지며, 게임과의 자동 API 연동은 하지 않는다. **채택된 문제는 관리자가 기존 저작 도구로 게임에 손수 입력**(반자동)하면 기존 파이프라인이 자동 배포한다.
- 커뮤니티 기여에는 보상이 따른다. 카페 닉네임과 게임 계정을 연결하지 않기 위해 **일회용 쿠폰 코드**로 보상한다: 채택 시 관리자가 코드를 발급해 카페 댓글로 전달하고, 플레이어는 게임에서 코드를 입력해 수령한다.
- **이 설계도는 (A) 문제에 제작자 크레딧을 남기는 확장, (B) 범용 쿠폰 코드 보상 시스템(신규 핵심), (C) 카페 운영 문서 산출을 다룬다.** 쿠폰 시스템은 이 용도 전용이 아니라 **범용**으로 지어 이벤트·공지 보상에도 재사용한다.
- 14 우편함과의 관계: 쿠폰 수령의 실제 보상 지급은 **14 우편함을 재활용**한다 — 쿠폰 서버는 검증 후 당사자 우편함에 보상 우편을 넣기만 하고, 지급·UI는 우편함이 처리한다. 90 관리자와의 관계: 쿠폰 발급 탭은 90 관리자 패널에 새 탭으로 붙고 `checkAdminKey` 인증을 재사용한다.

## 1. 목표 / 완료 정의

1. **제작자 크레딧**: `ProblemDef`에 제작자 이름 필드가 있고, 관리자 저작 도구(에디터·인게임 폼)에서 입력하며, R&E에서 그 문제를 풀고 난 해설 화면에 "이 문제는 ○○○ 님이 만들었습니다"가 표시된다(비어 있으면 표시 안 함).
2. **쿠폰 발급(관리자)**: 관리자 패널 쿠폰 탭에서 보상 항목(재화/결정 여러 개) + 사용 조건(최대 사용수·계정당 1회·만료일) + 메모를 입력해 코드를 발급하면 TitleData `coupons`에 저장된다. 발급 목록 조회·회수도 가능하다.
3. **쿠폰 수령(플레이어)**: 우편함 패널 상단의 코드 입력창에 코드를 입력하고 [받기]를 누르면, 유효한 코드면 보상이 우편으로 도착하고 곧바로 우편함 목록에 반영된다. 무효/만료/사용초과/이미수령 코드는 각각 다른 안내 메시지를 띄운다.
4. **1회성·조건 보장**: 같은 코드는 `maxUses`를 넘겨 수령할 수 없고, `계정당 1회` 코드는 한 계정이 두 번 못 받는다. 만료된 코드는 거부된다.
5. **범용성**: 쿠폰은 별점·문제와 무관한 자료구조다 — 관리자가 발급 시 보상을 직접 담으므로, 문제-기여 보상뿐 아니라 이벤트/공지 보상 코드로도 그대로 쓸 수 있다.
6. **운영 문서**: 카페 제출 양식과 채택·보상 운영 규칙 문서가 산출되어, 카페 필드가 `ProblemDef`에 1:1 매핑되고 관리자가 재입력 부담 없이 게임에 옮길 수 있다.

### 확정된 설계 결정
| # | 결정 | 근거 |
|---|------|------|
| 1 | 커뮤니티 = 네이버 카페(외부), 게임 자동 연동 없음. 채택 문제는 관리자가 수동 입력 | 사용자 선택(C 하이브리드, 반자동 허용) |
| 2 | 기여 보상 = 일회용 쿠폰 코드 방식. 카페 닉네임↔게임 계정 연결 안 함 | 사용자 선택 — 계정 연결 회피가 가장 편함 |
| 3 | 쿠폰 보상 지급 = **14 우편함 재활용**. 쿠폰 서버는 당사자 우편함에 보상 우편만 push, 지급·UI는 우편함이 담당 | 신규 지급 로직·지갑 동기화 불필요, 지갑 경합 회피 |
| 4 | 쿠폰은 **범용** 시스템(보상 항목 배열 + 사용조건). 별점/문제를 모름 | 사용자 선택(A 범용) — 이벤트 보상 재사용 |
| 5 | 보상 등급은 **별점**에만 연동(난이도 무관): 4.0~4.49=일반 재화, 4.5+=일반 재화+특별 보상 | 사용자 결정 |
| 6 | 특별 보상(한정 아이템·칭호)은 아직 미제작 → 잠정적으로 결정(Crystal) 재화로 대체 + 훅만 | 사용자 결정 — 나중에 제작 |
| 7 | 별점 집계·채택 판단은 카페에서 관리자가 수동. 게임/코드는 별점을 모름 | 네이버 카페엔 별점 기능 없음, 범용성 유지(결정 4) |
| 8 | 플레이어 코드 입력 UI = 우편함 패널 상단에 얹음(새 화면 안 만듦) | 보상이 우편함에 도착하므로 동선이 자연스러움 |
| 9 | 관리자 쿠폰 발급 UI = 90 관리자 패널에 새 탭 추가 | 90 패널·`checkAdminKey` 재사용 |

### 3-2. 쿠폰 데이터 모델 — `Coupon.cs` (신규)

**`Scripts/Meta/Coupon.cs`** (JsonUtility 호환 plain 클래스):
```csharp
using System;
using System.Collections.Generic;

/// <summary>쿠폰 보상 항목 1개. 14 우편함의 MailItem으로 변환되어 지급된다.</summary>
[Serializable]
public class CouponReward
{
    public int    attachType;   // MailAttachmentType 정수: 1 Currency / 2 Crystal / 3 Consumable
    public int    kindIndex;    // CurrencyKind / CrystalKind 인덱스
    public int    amount;
    public string title;        // 지급 우편 제목 (예: "커뮤니티 문제 채택 보상")
    public string body;         // 지급 우편 본문 (예: "★4.6 채택 감사합니다")
}

/// <summary>발급된 쿠폰 1건.</summary>
[Serializable]
public class Coupon
{
    public string code;              // 대문자 정규화된 코드 문자열
    public bool   active = true;     // 회수 시 false
    public List<CouponReward> rewards = new();
    public int    maxUses = 1;       // 1회용(문제-기여) 기본. 이벤트 전체공개는 큰 수
    public int    uses;              // 현재 사용 횟수
    public bool   perAccountOnce;    // true면 계정당 1회 (이벤트 코드용)
    public List<string> redeemers = new(); // perAccountOnce일 때 사용한 PlayFabId
    public long   expiresUtc;        // 0이면 무기한
    public string memo;              // 관리자 메모(어떤 문제/이벤트용인지)
}

/// <summary>TitleData "coupons" 직렬화 래퍼.</summary>
[Serializable]
public class CouponStore { public List<Coupon> coupons = new(); }
```
> 문제-기여 보상은 `maxUses=1, perAccountOnce=false`(그 코드는 한 번만 쓰이면 끝 = 특정 기여자용). 이벤트 코드는 `maxUses=큰수, perAccountOnce=true`(모두에게 공개하되 계정당 1회). 이 두 축으로 범용성을 확보한다.

**순수 검증 로직 분리** — `Coupon.cs`에 UI/서버 비의존 static 헬퍼를 두어 EditMode 테스트 가능하게:
```csharp
public enum CouponResult { Ok, NotFound, Inactive, Expired, MaxUsed, AlreadyRedeemed }

public static class CouponRules
{
    public static CouponResult Check(Coupon c, string playFabId, long nowUtc)
    {
        if (c == null)                            return CouponResult.NotFound;
        if (!c.active)                            return CouponResult.Inactive;
        if (c.expiresUtc != 0 && nowUtc >= c.expiresUtc) return CouponResult.Expired;
        if (c.uses >= c.maxUses)                  return CouponResult.MaxUsed;
        if (c.perAccountOnce && c.redeemers != null && c.redeemers.Contains(playFabId))
                                                  return CouponResult.AlreadyRedeemed;
        return CouponResult.Ok;
    }
}
```
> 서버(JS)와 클라(C#)가 같은 규칙을 갖지만, **최종 판정은 서버가 권위**를 가진다(아래 3-3). C# `CouponRules`는 테스트 + 클라 사전 표시용.

### 3-3. 서버 — `CloudScript/Coupons.js` (신규)

> Legacy CloudScript는 단일 스크립트다. 배포 순서에 이어붙인다:
> `VerifyAdminKey.js → ProblemAdmin.js → PlayerAdmin.js → Coupons.js`.
> `checkAdminKey`는 ProblemAdmin.js에 전역 정의됨 — **재정의 금지, 호출만**.

```js
function loadCouponStore() {
    var res = server.GetTitleData({ Keys: ["coupons"] });
    var raw = res.Data && res.Data.coupons;
    var store = raw ? JSON.parse(raw) : {};
    if (!store.coupons) store.coupons = [];
    return store;
}
function saveCouponStore(store) {
    server.SetTitleData({ Key: "coupons", Value: JSON.stringify(store) });
}
function findCoupon(store, code) {
    for (var i = 0; i < store.coupons.length; i++)
        if (store.coupons[i].code === code) return store.coupons[i];
    return null;
}

// ── 관리자: 발급 ─────────────────────────────────────────────
handlers.AdminCreateCoupon = function (args, context) {
    if (!checkAdminKey(args))                 return { success: false, error: "auth" };
    if (!args.coupon || !args.coupon.code)    return { success: false, error: "invalid" };

    var store = loadCouponStore();
    var code  = String(args.coupon.code).toUpperCase();
    if (findCoupon(store, code))              return { success: false, error: "duplicate" };

    args.coupon.code  = code;
    args.coupon.uses  = 0;
    if (!args.coupon.redeemers) args.coupon.redeemers = [];
    store.coupons.push(args.coupon);
    saveCouponStore(store);
    return { success: true };
};

// ── 관리자: 목록 / 회수 ──────────────────────────────────────
handlers.AdminListCoupons = function (args, context) {
    if (!checkAdminKey(args)) return { success: false, error: "auth" };
    var store = loadCouponStore();
    return { success: true, couponsJson: JSON.stringify(store) }; // {coupons:[...]}
};
handlers.AdminDeleteCoupon = function (args, context) {
    if (!checkAdminKey(args)) return { success: false, error: "auth" };
    if (!args.code)           return { success: false, error: "invalid" };
    var store = loadCouponStore();
    var code  = String(args.code).toUpperCase();
    store.coupons = store.coupons.filter(function (c) { return c.code !== code; });
    saveCouponStore(store);
    return { success: true };
};

// ── 플레이어: 수령 (관리자 키 불필요, 세션 티켓 + currentPlayerId) ──
handlers.RedeemCoupon = function (args, context) {
    if (!args.code) return { success: false, error: "invalid" };

    var store = loadCouponStore();
    var code  = String(args.code).toUpperCase();
    var c     = findCoupon(store, code);
    var now   = Date.now();

    if (!c)                                    return { success: false, error: "not_found" };
    if (!c.active)                             return { success: false, error: "inactive" };
    if (c.expiresUtc && now >= c.expiresUtc)   return { success: false, error: "expired" };
    if ((c.uses || 0) >= (c.maxUses || 1))     return { success: false, error: "max_used" };
    if (c.perAccountOnce && c.redeemers && c.redeemers.indexOf(currentPlayerId) !== -1)
                                               return { success: false, error: "already" };

    // 보상 → 당사자 우편함 push (AdminSendMail과 동일 로직)
    var res = server.GetUserData({ PlayFabId: currentPlayerId, Keys: ["mailbox"] });
    var raw = res.Data && res.Data.mailbox && res.Data.mailbox.Value;
    var box = raw ? JSON.parse(raw) : {};
    if (!box.mails) box.mails = [];
    var rewards = c.rewards || [];
    for (var i = 0; i < rewards.length; i++) {
        var r = rewards[i];
        box.mails.push({
            id:         "mail_" + Date.now() + "_" + Math.floor(Math.random() * 100000),
            sentUtc:    Date.now(),
            title:      r.title ? String(r.title) : "쿠폰 보상",
            body:       r.body  ? String(r.body)  : "",
            attachType: r.attachType | 0,
            kindIndex:  r.kindIndex  | 0,
            amount:     r.amount     | 0,
            read:       false,
            claimed:    false
        });
    }
    server.UpdateUserData({ PlayFabId: currentPlayerId, Data: { mailbox: JSON.stringify(box) } });

    // 사용 카운트 반영
    c.uses = (c.uses || 0) + 1;
    if (c.perAccountOnce) { if (!c.redeemers) c.redeemers = []; c.redeemers.push(currentPlayerId); }
    saveCouponStore(store);

    return { success: true, granted: rewards.length };
};
```
> **권위**: 검증·카운트·우편 push 전부 서버에서 원자적으로 처리한다. 클라는 결과만 받는다.
> **알려진 한계(경합)**: `coupons`는 TitleData read-modify-write라, 서로 다른 코드가 아니라 **동일 코드**를 여러 명이 같은 순간 수령하면 `uses` 증가가 유실될 이론적 여지가 있다. 소규모 게임에서 허용(YAGNI). `perAccountOnce`의 중복 방지는 `redeemers`로 사실상 보장된다.

    public static void Redeem(string code, Action<int> onOk, Action<string> onErr)
    {

            }, onErr);
    }

        "expired"   => "기한이 지난 코드입니다.",
        "max_used"  => "이미 모두 사용된 코드입니다.",
        "already"   => "이미 받은 코드입니다.",
        _           => "코드를 받을 수 없습니다.",
    };
    // IsSuccess / ErrorText 는 PlayerAdminService와 동일 구현 재사용

## 6. 엣지 케이스 / 주의점

| 상황 | 처리 |
|------|------|
| 동일 코드 동시 대량 수령 | TitleData read-modify-write 경합으로 `uses` 유실 여지 — 소규모 허용(YAGNI). `perAccountOnce`는 `redeemers`로 중복 방지 |
| 같은 계정이 1회용 코드 재입력 | 문제-기여용은 `maxUses=1` → 두 번째 수령 시 `max_used`. 계정당1회 이벤트 코드는 `already` |
| 만료일 지난 코드 | 서버가 `expired` 반환(만료 판정 서버 권위). `expiresUtc=0`이면 무기한 |
| 회수(`active=false`)된 코드 입력 | `inactive` 반환 |
| 특별 보상(한정 아이템/칭호) 미제작 | 4.5+ 등급은 잠정적으로 결정(Crystal) 재화 항목으로 발급. 향후 `MailAttachmentType` 확장(Consumable/신규 Title) 시 보상 항목 타입만 바꾸면 됨 — 쿠폰 구조 무변경 |
| 소비아이템(Consumable) 보상 | 14와 동일하게 12 상점 구현 전까지 `Mailbox.Claim`의 Consumable 분기가 no-op → 지급 보류. 현재는 재화/결정만 발급 권장 |
| 코드 대소문자·공백 | 서버·클라 모두 `trim + toUpperCase`로 정규화해 일치시킴 |
| 제작자 이름 개인정보 | 카페 닉네임만 받고 실명 금지(운영 규칙 문서에 명시). 표시용 문자열일 뿐 계정과 연결 안 됨 |
| authorName 구 데이터(필드 없음) | 역직렬화 시 null/빈 문자열 → 크레딧 미표시로 안전 |
| RedeemCoupon을 비로그인/세션만료 상태에서 호출 | `currentPlayerId` 없음 → CloudScript 자체가 실패, 클라 `onErr`로 처리 |
