# 14. 우편함 시스템

---

## 세계관 맥락

- 우편함은 **관리자(운영)가 개별 계정에 재화·과목 결정·소비 아이템·공지/경고 메시지를 보내고, 플레이어가 접속해서 수령/확인하는 통로**다.
- 기존 보상 지급은 두 갈래로 나뉘어 있었다: 13 출석·15 임무는 플레이어가 접속 중 버튼을 눌러 즉시 지급받고, 90 관리자는 CloudScript가 대상 세이브를 직접 수정해 "재로그인 시 반영"되는 방식이었다. 하지만 **관리자가 특정 계정에 보상이나 메시지를 남기고, 그 계정 소유자가 나중에 확인·수령하는 공통 통로**는 없었다.
- **이 설계도는 관리자 발송 → 대상 계정 저장 → 플레이어 수령/읽음까지 우편함 시스템의 데이터·저장 구조·서버 발송·UI 전체를 다룬다.**
- `설계도/90_관리자-시스템.md`가 계획했던 미구현 `AdminGiveCurrency`(즉시 재화 지급)와 `AdminSendWarning`(`KEY_WARNINGS` 경고 팝업)은 **이 설계도의 `AdminSendMail`로 흡수**됐다 — 온라인 즉시지급과 오프라인 경고라는 두 경로를 유지하지 않고 우편함 하나로 통일한다. 90번 문서는 이 결정에 맞춰 함께 수정됐다.

## 1. 목표 / 완료 정의

1. **관리자 발송 1사이클**: 관리자 패널 플레이어 탭에서 대상/제목/본문/첨부(없음·재화·과목결정·소비아이템)/수량 입력 → [발송] → 대상 계정 우편함에 우편 1건 추가.
2. **수령 접근**: 계정 패널(ESC) 하단에 우편함 버튼. 클릭 시 우편함 패널이 열리며 서버에서 최신 우편함을 재조회한다.
3. **개별 수령**: 첨부가 있는 우편의 [수령] 클릭 → 해당 재화/결정/소비아이템이 즉시 지급되고, 그 우편은 "수령완료"로 표시된다.
4. **전체 수령**: [모두 받기] 클릭 → 미수령 첨부 우편을 일괄 지급.
5. **메시지 확인**: 첨부 없는 공지/경고 우편은 [확인] 클릭 시 읽음 처리되지만, v1에서는 목록에서 사라지지 않는다(삭제 없음).
6. **안읽음 배지**: 계정 패널 우편함 버튼에 미확인(미읽음 메시지 + 미수령 보상) 개수가 표시된다.
7. **영속화**: 수령/읽음 상태가 PlayFab에 저장되어 재로그인 후에도 유지된다. 관리자가 보낸 우편은 플레이어의 일상적인 메타 자동저장에 의해 덮이지 않는다.
8. **만료 없음**: 우편은 수령/확인 여부와 무관하게 자동 삭제되지 않는다(공지 자동삭제는 후속 확장, §"후속" 참조).

### 확정된 설계 결정
| # | 결정 | 근거 |
|---|------|------|
| 1 | 발송 주체 = 관리자 직접 발송만. 자동 발송(시스템 트리거)은 이 설계도 범위 밖 | 사용자 요구 — "기본적으로 관리자가 직접 지급, 일부는 추후 자동화" |
| 2 | 첨부 종류 = 재화(`CurrencyKind`) · 과목 결정(`CrystalKind`) · 소비 아이템(`ConsumableKind`, 12 상점) · 없음(메시지 전용) | 사용자 요구. 캐릭터 지급은 90 관리자 캐릭터 탭이 이미 전담 — 우편함 범위 제외(중복 방지) |
| 3 | 보상 첨부 우편 = 만료 없음, 수령 전까지 영구 보관 | 사용자 요구 — "만료 없는 방식으로" |
| 4 | 공지/경고 메시지 = v1은 읽어도 삭제 안 됨. 시간경과 자동삭제는 후속 확장 | 사용자 요구 — "일단은 읽어도 사라지지는 않게" |
| 5 | 저장 구조 = **UserData 단일 저장**(플레이어 소유) + 관리자 CloudScript가 대상 UserData를 read-modify-write로 병합 | 사용자 선택(B안) |
| 6 | lost-update 완화 장치 2가지: (a) 우편함을 **독립 UserData 키("mailbox")**로 분리해 일상 메타 자동저장이 건드리지 않게 함, (b) 우편함 패널을 열 때마다 서버에서 **재조회**해 관리자가 보낸 최신 우편을 반영 | B안(단일 저장)을 유지하면서 "관리자 우편이 플레이어 저장에 덮여 사라지는" 위험을 구조적으로 최소화 |
| 7 | 수령 처리 = 클라이언트가 즉시 재화/결정/소비아이템 지급(기존 `Wallet.Add`/`Crystals.Add`와 동일한 신뢰 모델). 수령 시 CloudScript 왕복 없음 | 13 출석·15 임무의 기존 지급 패턴 재사용. 신규 서버 코드 최소화 |
| 8 | UI 진입점 = `AccountPanel`(ESC) 버튼 + 안읽음 배지. 별도 HUD 아이콘·허브 건물 없음 | 사용자 요구 — "계정 패널 아래에 우편함 버튼" |
| 9 | 개별 수령 + 전체 수령([모두 받기]) 둘 다 지원 | 사용자 요구 |

| 재화/결정 enum | `Scripts/Meta/CurrencyKind.cs`(Gold/Paper/Focus/Fragment), `Scripts/Meta/CrystalKind.cs` | 첨부 `kindIndex` 매핑 기준 |
| 소비 아이템(12 상점, 미구현) | 설계도 `12_상점-시스템.md`의 `ConsumableKind`/`ConsumableInventory` | **아직 코드 없음**. 첨부 enum 값은 정의하되, 지급 로직은 `MetaState.Consumables` 존재 여부로 가드(§6 참조) |

> **핵심 정합성**: 관리자 발송은 대상 계정이 오프라인이어도 동작해야 하므로 서버(CloudScript)에서 직접 UserData를 쓴다. 반대로 플레이어의 일상적인 메타 저장(`MetaSaveService.Save()`)은 로그인 세션 동안 여러 번 도는데, 이 배치 저장이 mailbox 키를 함께 쓰면 관리자가 그 사이 보낸 우편을 덮어써버릴 수 있다. 이를 막기 위해 mailbox는 배치 저장에서 완전히 분리된 독립 키로 취급한다(결정 6).

## 3. 아키텍처

### 3-1. 데이터 모델 — `MailItem.cs` (신규)

**`Scripts/Meta/MailItem.cs`**:
```csharp
using System;

/// <summary>우편 첨부 종류. None = 첨부 없는 공지/경고 메시지.</summary>
public enum MailAttachmentType { None, Currency, Crystal, Consumable }

/// <summary>우편 1건. 관리자 발송(서버) 또는 추후 시스템 발송으로 생성된다.</summary>
[Serializable]
public class MailItem
{
    public string id;               // 서버에서 생성 (timestamp+rand)
    public long   sentUtc;          // 발송 시각 (Unix seconds) — 후속 자동삭제 확장 훅
    public string title;
    public string body;
    public MailAttachmentType attachType;
    public int    kindIndex;        // attachType별 enum 인덱스 (CurrencyKind/CrystalKind/ConsumableKind)
    public int    amount;
    public bool   read;             // 메시지 확인 또는 보상 수령 시 true
    public bool   claimed;          // 첨부 지급 완료 여부 (attachType == None이면 항상 false)
}
```
> `attachType == None`인 메시지는 `claimed`가 의미 없다 — `read`만으로 상태를 표현한다. 보상 우편은 `claimed`가 최종 상태이며, `Claim` 성공 시 `read`도 함께 true로 세팅한다(수령 = 확인을 포함).

**`Scripts/Meta/MailboxData.cs`** (또는 `MailItem.cs`에 동봉):

### 3-2. 런타임 저장소 — `Mailbox.cs` (신규)

**`Scripts/Meta/Mailbox.cs`** (`Wallet.cs`/`Roster.cs` 패턴 모방):
```csharp
using System;
using System.Collections.Generic;

public class Mailbox
{
    public event Action OnChanged;

    List<MailItem> _mails = new();
    public IReadOnlyList<MailItem> Mails => _mails;

    /// <summary>미확인 개수 = 미읽음 메시지 + 미수령 보상.</summary>
    public int UnreadCount()
    {
        int n = 0;
        foreach (var m in _mails)
        {
            bool pending = m.attachType == MailAttachmentType.None ? !m.read : !m.claimed;
            if (pending) n++;
        }
        return n;
    }

    public bool MarkRead(string id)
    {
        var m = Find(id);
        if (m == null || m.read) return false;
        m.read = true;
        OnChanged?.Invoke();
        return true;
    }

    /// <summary>첨부 지급 + claimed 세팅. 이미 claimed면 멱등(false, 재지급 없음).</summary>
    public bool Claim(string id)
    {
        var m = Find(id);
        if (m == null || m.attachType == MailAttachmentType.None || m.claimed) return false;

        switch (m.attachType)
        {
            case MailAttachmentType.Currency:
                MetaState.Wallet.Add((CurrencyKind)m.kindIndex, m.amount);
                break;
            case MailAttachmentType.Crystal:
                MetaState.Crystals.Add((CrystalKind)m.kindIndex, m.amount);
                break;
            case MailAttachmentType.Consumable:
                MetaState.Consumables?.Add(m.kindIndex, m.amount); // 12 미구현 시 no-op
                break;
        }
        m.claimed = true;
        m.read = true;
        OnChanged?.Invoke();
        return true;
    }

    /// <summary>미수령 보상 우편 전체 수령. 반환값 = 수령 건수.</summary>
    public int ClaimAll()
    {
        int n = 0;
        foreach (var m in _mails)
            if (m.attachType != MailAttachmentType.None && !m.claimed && Claim(m.id)) n++;
        return n;
    }

    MailItem Find(string id) { foreach (var m in _mails) if (m.id == id) return m; return null; }

    public MailboxData Export() => new MailboxData { mails = new List<MailItem>(_mails) };
    public void LoadState(MailboxData data)
    {
        _mails = (data?.mails) ?? new List<MailItem>();
        OnChanged?.Invoke();
    }
}
```
> `Claim`이 `ClaimAll` 내부에서 매번 `OnChanged`를 발행하지만, 이번 스코프에선 문제 없음(YAGNI로 배치 이벤트 억제는 생략). `MetaState.Consumables`는 12 상점 구현 전까지 null이며, `?.Add`로 안전하게 무시된다 — 구현 후 자동으로 연동된다.

### 3-3. 저장/동기화 — `MetaSaveService.cs` 확장

```csharp
const string KEY_MAILBOX = "mailbox";

/// <summary>우편함만 저장. 일반 배치 Save()와 분리 — 관리자 발송이 덮이지 않도록.</summary>
public static void SaveMailbox(Action onDone = null, Action<string> onError = null)
{
    if (!PlayFabClientAPI.IsClientLoggedIn()) { onDone?.Invoke(); return; }
    var data = new Dictionary<string, string> { { KEY_MAILBOX, JsonUtility.ToJson(MetaState.Mailbox.Export()) } };
    PlayFabClientAPI.UpdateUserData(new UpdateUserDataRequest { Data = data },
        _ => onDone?.Invoke(),
        err => onError?.Invoke(err.GenerateErrorReport()));
}

/// <summary>우편함을 서버에서 재조회. 우편함 패널 Open 시 호출.</summary>
public static void RefreshMailbox(Action onDone = null, Action<string> onError = null)
{
    PlayFabClientAPI.GetUserData(new GetUserDataRequest { Keys = new List<string> { KEY_MAILBOX } },
        result =>
        {
            if (result.Data != null && result.Data.TryGetValue(KEY_MAILBOX, out var mb))
                MetaState.Mailbox.LoadState(JsonUtility.FromJson<MailboxData>(mb.Value));
            onDone?.Invoke();
        },
        err => onError?.Invoke(err.GenerateErrorReport()));
}
```

**기존 `Load()` 수정** — 로그인 시 mailbox 키도 함께 읽도록 `Keys` 목록과 파싱 분기에 `KEY_MAILBOX` 추가(위 `RefreshMailbox`와 동일 로직, 최초 1회는 `Load()`가 겸함).

**기존 `Save()`는 무수정** — `KEY_WALLET`/`KEY_ROSTER`/`KEY_GACHA`/`KEY_CRYSTALS`/`KEY_STUDY`만 다루던 그대로 유지한다. `KEY_MAILBOX`를 여기 추가하지 않는 것이 이 설계의 핵심 안전장치다(결정 6-a).

### 3-4. 관리자 발송 — `CloudScript/PlayerAdmin.js` 확장

```js
handlers.AdminSendMail = function (args, context) {
    if (!checkAdminKey(args))     return { success: false, error: "auth" };
    if (!args.playFabId)          return { success: false, error: "invalid id" };
    if (!args.title)              return { success: false, error: "title required" };

    var res = server.GetUserData({ PlayFabId: args.playFabId, Keys: ["mailbox"] });
    var raw = res.Data && res.Data.mailbox ? res.Data.mailbox.Value : null;
    var box = raw ? JSON.parse(raw) : { mails: [] };

    box.mails.push({
        id:         "mail_" + Date.now() + "_" + Math.floor(Math.random() * 10000),
        sentUtc:    Math.floor(Date.now() / 1000),
        title:      args.title,
        body:       args.body || "",
        attachType: args.attachType || 0,   // MailAttachmentType 정수값
        kindIndex:  args.kindIndex  || 0,
        amount:     args.amount     || 0,
        read:       false,
        claimed:    false
    });

    server.UpdateUserData({
        PlayFabId: args.playFabId,
        Data: { mailbox: JSON.stringify(box) }
    });

    return { success: true };
};
```
> **read-modify-write 경합**: 관리자가 같은 대상에게 짧은 시간 내 연속 발송하면 마지막 쓰기가 이전 발송을 덮을 이론적 위험이 있다. 관리자 조작은 저빈도·수동이라 실사용 위험은 낮음(YAGNI로 낙관적 락 생략, 필요 시 후속 확장).

**클라 발송** — `Backend/PlayerAdminService.cs`:
```csharp
public static void SendMail(string playFabId, string title, string body,
    MailAttachmentType attachType, int kindIndex, int amount,
    Action onOk, Action<string> onErr)
{
    CloudScriptService.Execute("AdminSendMail",
        new { key = MetaState.AdminKey, playFabId, title, body,
              attachType = (int)attachType, kindIndex, amount },
        _ => onOk?.Invoke(),
        onErr);
}
```

## 6. 엣지 케이스 / 주의점

| 상황 | 처리 방식 |
|------|----------|
| 소비 아이템 첨부, 12 상점 미구현 | `MetaState.Consumables`가 null → `Claim`의 Consumable 분기가 `?.Add`로 안전 무시. enum 값은 미리 정의해 두되, 실제 지급은 12 구현 후 자동 연동 |
| 관리자가 짧은 시간 내 같은 대상에 연속 발송 | 서버 read-modify-write 경합으로 이론상 한 건이 덮일 수 있음. 관리자 조작은 저빈도·수동이라 v1은 허용(YAGNI), 필요해지면 서버 측 재시도/락 후속 추가 |
| 플레이어가 우편함을 연 직후 관리자가 발송 | 그 사이 우편은 다음 `RefreshMailbox` 호출(패널 재오픈)까지 보이지 않음 — 인지된 트레이드오프, 자동 폴링은 범위 밖(YAGNI) |
| 일반 메타 자동저장(`Save()`) 도중 관리자 발송 | `Save()`가 mailbox 키를 다루지 않으므로 **영향 없음** — 이 설계의 핵심 안전장치 |
| 구 세이브(mailbox 키 없음) | `RefreshMailbox`/`Load()`에서 `raw == null` → 빈 목록으로 초기화. 에러 아님 |
| 이미 claimed인 우편에 다시 [수령] 클릭 | `Claim`이 false 반환, 재지급 없음(멱등) — UI도 버튼을 즉시 비활성화해 이중클릭 방지 |
| `ClaimAll` 중 일부만 성공 | 개별 `Claim` 실패(이미 claimed 등)는 카운트에서 제외될 뿐 전체 흐름은 중단되지 않음 |
| 공지/경고 메시지 v1 삭제 없음 | 목록이 계속 늘어남 — 후속 확장(자동삭제)까지는 관리자가 남발하지 않는 것으로 운영 대응. `sentUtc` 필드가 이미 있어 확장 시 스키마 변경 불필요 |
| 첨부 타입 `None`인데 `Claim` 호출 | `attachType == None` 조건으로 즉시 false 반환 — 메시지는 `MarkRead`만 유효 |
| 대상 PlayFabId 오타/미존재 | 발송 폼은 자유입력을 받지 않는다 — 90 플레이어 탭의 `AdminGetPlayers` 검색·목록·선택 라디오를 그대로 재사용해 목록에서 고른 대상만 발송 가능(§3-5) |
